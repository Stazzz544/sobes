# Правила составления вопросов

Банк вопросов — `src/entities/question/data/<topic>[-N].ts`, подключение — `data/index.ts`, теги — `config/tags.ts`.

## Перед коммитом

`npm run verify:content` — type-check + проверка банка. Перед релизом — `npm run verify:content -- --links` (живость всех источников).

## Чек-лист вопроса

- **Ровно один верный ответ**, однозначно. Если спорно — переформулировать или выкинуть.
- **Дистракторы правдоподобны, но точно неверны**: типичные заблуждения, перепутанные понятия, «почти правильные» варианты. Никаких «всё перечисленное» / «ничего из перечисленного».
- **Без подвохов в формулировке**: проверяем знание, а не внимательность к запятым.
- **Актуальность**: ES2024+, TypeScript 5.x, React 19, текущие стандарты (INP вместо FID и т.п.). Устаревшее — только с пометкой «до версии X».
- **RU и EN эквивалентны по смыслу.** Варианты, которые зависят от языка, — `text: { ru, en }`; `code` — только для языконезависимого (вывод программы, типы, фрагменты кода). Кириллица в `code` запрещена скриптом.
- **Пояснение** объясняет, почему верный ответ верен и почему популярные неверные — нет; пример кода, если помогает. Inline-код — в бэктиках, акцент — `**жирным**`.
- **Источники** — первоисточники (MDN, react.dev, typescriptlang.org, tc39, RFC, web.dev, OWASP, официальная документация инструментов), ссылка на конкретный раздел.
- **Метаданные**: `difficulty` 1 (junior) / 2 (middle) / 3 (senior), `popular: true` — если вопрос реально встречается на большинстве собеседований. На тему держать ~25% senior.
- **id** — `<prefix>-<тема>-NNN`, никогда не меняется (на нём хранится прогресс пользователей).

## Машинная проверка (`verify`)

Где возможно — обязательно:

| kind | Что проверяет |
| --- | --- |
| `js-output` | Код запускается в Node, stdout (пробелы схлопнуты) = код верного варианта; ни один другой вариант не совпадает |
| `ts-type` | Тип переменной `symbol` из компилятора = код верного варианта (объединения сравниваются как множества) |
| `ts-check` | Код вопроса + `source` компилируется без ошибок; ожидаемые ошибки помечать `// @ts-expect-error`; точный тип — через хелпер `Equal` |
| `ts-error` | Код вопроса даёт ошибки только с указанным кодом (например, `2322`) |
| `ts-output` | TS транспилируется и запускается, как `js-output` |
| `css-computed` | Код вопроса (`css` → в `<style>`, `html` — как есть) + `html` рендерится в headless Chrome в iframe 800×600 (`viewportWidth` меняет ширину); значение `property` у `selector` = `expected`, а без него — коду верного варианта. `property`: любое CSS-свойство из `getComputedStyle` или `rect.width/height/top/left` из `getBoundingClientRect`; `selector` может содержать `::before`. `also` — дополнительные проверки на той же странице |

Для `css-computed` нужен Chrome или Edge (стандартные пути или `CHROME_PATH`); без браузера скрипт пишет предупреждение и эти вопросы не проверяет, а в CI (`CI=true`) падает. Учитывать стили браузера по умолчанию: `body { margin: 8px }`, шрифт 16px, цвет текста `rgb(0, 0, 0)`. `getComputedStyle` возвращает вычисленное значение и для неприменимых свойств (`width` у строчного элемента вернёт заданное, а не `auto`) — такое проверять через `rect.*`.

Для концептуальных вопросов (React, Web) спорные утверждения сверять с первоисточником; поведение, которое можно проверить (Node, компилятор, браузер), — проверять запуском.
