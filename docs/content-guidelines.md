# Правила составления вопросов

Банк вопросов — `src/entities/question/data/<topic>[-N].ts`, подключение — `data/index.ts`, теги — `config/tags.ts`.

## Перед коммитом

`npm run verify:content` — type-check + проверка банка. Перед релизом — `npm run verify:content -- --links` (живость всех источников).

## Чек-лист вопроса

- **Ровно один верный ответ**, однозначно. Если спорно — переформулировать или выкинуть.
- **Дистракторы правдоподобны, но точно неверны**: типичные заблуждения, перепутанные понятия, «почти правильные» варианты. Никаких «всё перечисленное» / «ничего из перечисленного».
- **Без подвохов в формулировке**: проверяем знание, а не внимательность к запятым.
- **Актуальность**: ES2024+, TypeScript 5.x, React 19, текущие стандарты (INP вместо FID и т.п.). Устаревшее — только с пометкой «до версии X».
- **RU и EN эквивалентны по смыслу.** Варианты, которые зависят от языка, — `text: { ru, en }`; `code` — только для языконезависимого (вывод программы, типы, фрагменты кода). Кириллица в `code` запрещена скриптом.
- **Пояснение** объясняет, почему верный ответ верен и почему популярные неверные — нет; пример кода, если помогает. Inline-код — в бэктиках, акцент — `**жирным**`.
- **Источники** — первоисточники (MDN, react.dev, typescriptlang.org, tc39, RFC, web.dev, OWASP, официальная документация инструментов), ссылка на конкретный раздел.
- **Метаданные**: `difficulty` 1 (junior) / 2 (middle) / 3 (senior), `popular: true` — если вопрос реально встречается на большинстве собеседований. На тему держать ~25% senior.
- **id** — `<prefix>-<тема>-NNN`, никогда не меняется (на нём хранится прогресс пользователей).

## Машинная проверка (`verify`)

Где возможно — обязательно:

| kind | Что проверяет |
| --- | --- |
| `js-output` | Код запускается в Node, stdout (пробелы схлопнуты) = код верного варианта; ни один другой вариант не совпадает |
| `ts-type` | Тип переменной `symbol` из компилятора = код верного варианта (объединения сравниваются как множества) |
| `ts-check` | Код вопроса + `source` компилируется без ошибок; ожидаемые ошибки помечать `// @ts-expect-error`; точный тип — через хелпер `Equal` |
| `ts-error` | Код вопроса даёт ошибки только с указанным кодом (например, `2322`) |
| `ts-output` | TS транспилируется и запускается, как `js-output` |
| `shell-output` | Код (`bash`) выполняется в пустой временной папке с чистым `HOME`: свой `.gitconfig` (ветка по умолчанию `main`, автор Sobes), фиксированные даты коммитов, `LC_ALL=C`; stdout сравнивается, как в `js-output`. Шум команд убирать флагами `-q` или `> /dev/null`, ожидаемо падающие команды — `\|\| true` (скрипт идёт с `set -e`). Нужен bash: Git Bash на Windows (`BASH_PATH` — свой путь), в CI — системный |
| `css-computed` | Код вопроса (`css` → в `<style>`, `html` — как есть) + `html` рендерится в headless Chrome в iframe 800×600 (`viewportWidth` меняет ширину); значение `property` у `selector` = `expected`, а без него — коду верного варианта. `property`: любое CSS-свойство из `getComputedStyle` или `rect.width/height/top/left` из `getBoundingClientRect`; `selector` может содержать `::before`. `also` — дополнительные проверки на той же странице |

Для `css-computed` нужен Chrome или Edge (стандартные пути или `CHROME_PATH`); без браузера скрипт пишет предупреждение и эти вопросы не проверяет, а в CI (`CI=true`) падает. Учитывать стили браузера по умолчанию: `body { margin: 8px }`, шрифт 16px, цвет текста `rgb(0, 0, 0)`. `getComputedStyle` возвращает вычисленное значение и для неприменимых свойств (`width` у строчного элемента вернёт заданное, а не `auto`) — такое проверять через `rect.*`.

Для концептуальных вопросов (React, Web) спорные утверждения сверять с первоисточником; поведение, которое можно проверить (Node, компилятор, браузер), — проверять запуском.

## HR и поведенческие вопросы

«Один верный ответ» здесь получается, если спрашивать не «что сказать», а **какой ответ сильнее**: верный вариант опирается на источник (карьерные центры университетов, Google re:Work, ТК РФ), дистракторы — типичные ошибки кандидатов (критика бывшего работодателя, «перфекционист», «сколько дадите», «вопросов нет»).

- Варианты — `text { ru, en }` одинаковой длины и тона; верный не должен выделяться только объёмом.
- Факты (сроки по ТК РФ, ставка НДФЛ) — со ссылкой на закон или ФНС; расчёты оформлять `output` + `js-output`, чтобы их проверял скрипт.
- `bug-line` для HR не подходит: код не переводится, а построчный разбор ответа зависит от языка.
- Сложность по умолчанию 1–2; `verify-content` предупреждает о малом числе senior-вопросов — для HR это ожидаемо.

## Типы вопросов (`kind`)

По умолчанию вопрос — выбор из 5 вариантов (`kind` не указывается). Для активного вспоминания есть ещё три вида; `prompt`, `explanation`, `sources`, метаданные — как у обычного. id — с видом в теме: `js-event-loop-order-001`, `ts-narrowing-bug-001`, `css-units-output-001`.

| kind | Поля | Как отвечают | `verify` |
| --- | --- | --- | --- |
| `order` | `items` — 3–6 элементов **в правильном порядке** (`code` или `text`) | Нажимают элементы по порядку, нажатие на выбранный — убирает | `js-output`: stdout = коды `items` через пробел |
| `bug-line` | `code` (≥ 3 строк), `answerLine` — номер строки с 1 | Нажимают строку кода | `ts-error-line`: ошибки компилятора только на `answerLine` |
| `output` | `code`, `answers` — первый канонический, дальше допустимые написания (`'20px'`, `'20'`) | Вписывают ответ; пробелы при сравнении не учитываются | `js-output` / `ts-output` / `css-computed`: факт = `answers[0]` |

- **order**: порядок должен быть однозначным. Если два шага идут параллельно (DOM и CSSOM) — объединить их в один элемент. Элементы перемешиваются при показе.
- **bug-line**: ошибка ровно в одной строке, и её исправление — правка этой строки. В `prompt` описать симптом («возвращает NaN», «зацикливается»), а не намекать на место. Логические баги JS/React машинно не проверяются — запустить код вручную и убедиться, что симптом воспроизводится.
- **output**: ответ — короткий вывод без кириллицы; все разумные написания (с кавычками и без, с единицей и без) — в `answers`.
- Новый вид — не повод повторить существующий вопрос другой формой: перед добавлением искать в `data/` по ключевому фрагменту кода и по ссылке-источнику.

## Конспекты

Конспект — 1–2 экрана теории на тег: `src/entities/question/lessons/<тема>.ts`, подключение — `lessons/index.ts` (`LESSON_GROUPS`). Открывается из разбора вопроса и из «Слабых мест».

- **Структура**: `summary` (1–2 предложения — суть), `blocks` (те же `text` / `code` / `diagram`, что в разборе), `keyPoints` — 3–5 пунктов «Запомнить», `sources` — первоисточники.
- **Объём**: до ~350 слов на язык. Дать модель, из которой ответы на вопросы тега следуют, а не пересказывать разборы.
- **Каждый тег из `config/tags.ts` обязан иметь конспект** — `verify-content` падает, если его нет. Новый тег = новый конспект.
- **Код**: короткий, вывод — комментарием в конце строки (`// 3 1`), комментарии только на английском (кириллица в коде запрещена скриптом). Перед коммитом запустить каждый фрагмент в Node и сверить вывод с комментарием.
- **Схема** из `DIAGRAMS` — только вместе с тем кодом, который она иллюстрирует.
- `verify-content` проверяет: тег лежит в файле своей темы, нет дублей, RU и EN непустые, 3–5 пунктов, источники по https, нет кириллицы в коде; `--links` проверяет и источники конспектов.

## Глоссарий

Термин в тексте разбора или конспекта размечается как `[[id|текст]]` — в приложении он подчёркнут и по нажатию открывает карточку с определением. Термины — `src/entities/question/glossary/glossary.ts` (`term` и `definition` на RU и EN).

- Размечать первое упоминание термина в тексте, а не каждое.
- RU и EN одного текста должны ссылаться на одни и те же термины — `verify-content` проверяет это и то, что термин есть в глоссарии.
- Разметка работает в текстовых блоках (`text`) разборов и конспектов; в формулировках, вариантах, введении и «Запомнить» не используется.
