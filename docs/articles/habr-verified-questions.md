# Вопросы для собеседований, которые проверяет машина: Node.js, компилятор TypeScript, Chrome и git в одном CI

*Черновик для Хабра. Хабы: JavaScript, TypeScript, Тестирование веб-сервисов, Карьера в IT-индустрии. Перед публикацией: ссылка на RuStore, скриншоты 1–3 из `docs/store/screenshots/`.*

---

Я делаю Sobes — тренажёр для подготовки к собеседованиям фронтенд-разработчика: вопрос, пять вариантов, разбор со ссылками на первоисточники. Сейчас в банке 808 вопросов на русском и английском, от `this` и event loop до Next.js, доступности и git.

Самая неприятная часть такого проекта — не код приложения, а достоверность вопросов. В подборках «топ-100 вопросов по JavaScript» ошибки встречаются постоянно: неверный порядок вывода, устаревшее поведение, вариант, который «тоже правильный». Тренажёр с ошибкой в ответе хуже, чем никакой: человек выучит неправду и уверенно скажет её на собеседовании.

Поэтому я исходил из простого правила: **если утверждение можно проверить запуском — его проверяет машина, а не я**. Сейчас так проверяется 334 вопроса из 808 — 41%. Расскажу, как это устроено и что проверка нашла.

## Вопрос — это данные с полем `verify`

Вопросы лежат в TypeScript-файлах как обычные объекты. У тех, что можно проверить, есть поле `verify` — оно говорит, чем проверять:

```ts
{
  id: 'js-event-loop-001',
  prompt: { ru: 'В каком порядке выведутся значения?', en: '…' },
  code: {
    lang: 'js',
    source: `console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');`,
  },
  options: [{ code: '1 2 3 4' }, { code: '1 4 3 2' }, { code: '1 4 2 3' }, { code: '1 3 4 2' }, { code: '4 1 3 2' }],
  answer: 'b',
  verify: { kind: 'js-output' },
  // разбор, источники…
}
```

Скрипт `verify-content` проходит по всему банку и для каждого `kind` вызывает свой проверяльщик. Сейчас их десять:

| `verify.kind` | Чем проверяется | Вопросов |
| --- | --- | --- |
| `js-output` | запуск в Node.js | 143 |
| `css-computed` | `getComputedStyle` в headless Chrome | 46 |
| `shell-output` | настоящий git во временном репозитории | 40 |
| `dom-probe` | DOM и дерево доступности в Chrome | 36 |
| `ts-check` | утверждение на уровне типов | 23 |
| `js-tests` | автотесты на `node:assert` | 17 |
| `ts-type` | выведенный тип переменной | 15 |
| `ts-error` | код ошибки компилятора | 10 |
| `ts-output`, `ts-error-line` | транспиляция + запуск, строка ошибки | 4 |

Остальные 474 — вопросы, где запускать нечего: «какой ответ на HR-интервью сильнее», поведение React без DOM-окружения, архитектурные компромиссы. Для них обязательны источники, и их живость тоже проверяется (об этом ниже).

## JavaScript: запустить и сравнить

`js-output` — самый простой и самый полезный вид. Код вопроса пишется во временный файл, запускается отдельным процессом `node`, вывод нормализуется (пробелы и переводы строк схлопываются) и сравнивается:

- для вопроса с вводом ответа — с эталонным ответом;
- для вопроса с вариантами — с правильным вариантом, **и** проверяется, что ни один другой вариант не совпадает с фактическим выводом.

Второе условие важнее, чем кажется. Ошибка «правильный ответ неверен» встречается редко — её замечаешь сразу. А вот «дистрактор случайно тоже верен» глазами не видно: например, вариант `1 4 3 2` и `1 4 3 2 ` с лишним пробелом, или два варианта, отличающиеся только кавычками в выводе объекта.

Проверку я проверил тем же способом: подменил правильный ответ, порядок строк и строку с ошибкой — все три подмены `verify-content` поймал.

Одна тонкость — версия Node. Тексты ошибок V8 меняются между версиями: `TypeError: Cannot read properties of undefined (reading 'x')` когда-то звучал иначе. Если вопрос «что выведет код» включает текст ошибки, ответ зависит от версии движка. Поэтому версия Node в CI зафиксирована той же, на которой вопросы сверены локально.

## TypeScript: компилятор как оракул

Для TypeScript запускать код мало — интересны типы. Проверка использует Compiler API напрямую: код вопроса подсовывается компилятору как виртуальный файл, без записи на диск.

```ts
const compile = (source: string) => {
  const host = ts.createCompilerHost(COMPILER_OPTIONS);
  const originalGetSourceFile = host.getSourceFile;
  host.getSourceFile = (fileName, languageVersion, ...rest) =>
    fileName === VIRTUAL_FILE
      ? ts.createSourceFile(fileName, source, languageVersion, true)
      : originalGetSourceFile.call(host, fileName, languageVersion, ...rest);
  // …fileExists аналогично
  const program = ts.createProgram([VIRTUAL_FILE], COMPILER_OPTIONS, host);
  return { program, diagnostics: ts.getPreEmitDiagnostics(program) };
};
```

Дальше четыре режима:

- **`ts-type`** — «какой тип у `result`?». Находим объявление переменной, берём `checker.typeToString(checker.getTypeAtLocation(identifier))` и сравниваем с ответом.
- **`ts-error`** — «скомпилируется ли код?». Ожидается **ровно одна** конкретная ошибка, например `TS2322`. Если ошибок нет или появилась другая — вопрос сломан.
- **`ts-error-line`** — для вопросов «нажми строку с ошибкой»: все диагностики должны указывать на эту строку.
- **`ts-check`** — утверждение на уровне типов. К коду вопроса дописывается проверка, которая компилируется только при верном ответе:

```ts
type Equal<X, Y> = (<V>() => V extends X ? 1 : 2) extends (<V>() => V extends Y ? 1 : 2) ? true : false;
const check: Equal<User, { id: number; name: string }> = true;
```

`Equal` через обобщённые функции строже наивного `X extends Y ? Y extends X ? …`: он различает `any` и конкретный тип, `readonly` и модификаторы опциональности.

## CSS и HTML: спросить у браузера

Утверждения про каскад, блочную модель и доступность проверяет headless Chrome. Запускать браузер на каждый вопрос долго, поэтому все вопросы собираются в одну страницу: каждый — в свой `iframe` через `srcdoc`, а скрипт на странице опрашивает их и складывает результаты в `<pre>`:

```js
if (probe.property === 'aom.role') return element.computedRole;
if (probe.property === 'aom.name') return element.computedName;
if (probe.property.startsWith('rect.')) return element.getBoundingClientRect()[probe.property.slice(5)] + 'px';
return frame.defaultView.getComputedStyle(element, pseudo).getPropertyValue(probe.property);
```

Chrome запускается с `--headless --dump-dom`: он загружает страницу, выполняет скрипт и печатает итоговый DOM — оттуда и читается результат (в base64, чтобы не возиться с экранированием). Флаг `--enable-blink-features=ComputedAccessibilityInfo` включает `computedRole` и `computedName` — роль и доступное имя элемента в том виде, в каком их получит скринридер.

Так проверяется, например, что `margin-left: auto` во flex прижимает элемент вправо, что `:where()` даёт нулевую специфичность, что `aria-labelledby` важнее `aria-label`, а `<section>` без доступного имени не становится ориентиром `region`. У проверки есть ширина вьюпорта, поэтому сюда же попадают медиазапросы и `min()`.

На GitHub Actions пришлось добавить `--no-sandbox`: на ubuntu-раннерах AppArmor запрещает песочнице Chrome user namespaces. Страница наша локальная, так что риск здесь нулевой.

## Git: настоящий репозиторий на каждый вопрос

Вопросы про git проверяются запуском bash-скрипта в чистом временном репозитории. Чтобы вывод был одинаковым на моей машине и в CI, окружение зафиксировано:

```ts
spawnSync(bash, [script], {
  cwd: repo,
  env: {
    ...process.env,
    HOME: home,                       // свой .gitconfig: имя, ветка main, без GPG
    GIT_CONFIG_NOSYSTEM: '1',
    GIT_AUTHOR_DATE: '2026-01-01T00:00:00Z',
    GIT_COMMITTER_DATE: '2026-01-01T00:00:00Z',
    LC_ALL: 'C',
  },
});
```

Фиксированные даты дают одинаковые хеши коммитов, пустой системный конфиг — одинаковое поведение `pull`, `merge` и `init`. Главный урок: **не делать ответом текст ошибки git** — сообщения меняются между версиями. Вопрос «что произойдёт» лучше сводить к коду выхода (`echo $?`) или к состоянию репозитория (`git log --oneline`).

## Live-coding: тесты для вариантов ответа

Для задач в духе «напишите debounce» появился вид `js-tests`: к вопросу прикладываются тесты на `node:assert`, и проверяльщик гоняет их по-разному в зависимости от типа вопроса:

- **выбор из пяти реализаций** — тесты проходит только правильная, остальные четыре падают;
- **«расставьте строки по порядку»** — проходит правильный порядок, а каждая перестановка соседних строк ломает тесты (иначе порядок неоднозначен);
- **«найдите строку с багом»** — исходный код тесты валит, а код с заменённой строкой проходит.

Требование «перестановка соседних строк должна падать» отсекает задачи, где две строки можно поменять местами без последствий: у такого вопроса «расставьте по порядку» два правильных ответа, и человек, ответивший верно, получил бы «неверно».

## Что нашла проверка

Самые интересные находки — расхождения браузера со спецификацией и с моими ожиданиями:

- `<a>` без `href`, но с `onclick` Chrome отдаёт с ролью `link`, хотя по спецификации это `generic`. Вопрос пришлось переписать без обработчика, а нюанс вынести в разбор.
- `<header>` внутри `<article>` Chrome уже отдаёт с ролью ARIA 1.3 `sectionheader`. Я ожидал `generic` и поправил вопрос под фактическое поведение.
- `<img alt="">` по спецификации — `presentation`, но `computedRole` возвращает `image`. Такой вопрос машинная проверка не покрывает — он проверен по спецификации вручную.

Отдельный класс ошибок — не фактические, а форматные: проверка требует, чтобы в коде вариантов не было кириллицы, а варианты «все перечисленные» и «ничего из перечисленного» запрещены. Это не про корректность, а про качество вопроса: такие варианты угадываются без знаний.

## Проверка не только кода

Раз уж есть скрипт, который знает структуру банка, в него переехали и остальные правила:

- **Источники живы.** С флагом `--links` проверяются все 865 ссылок из разборов и конспектов. Сетевые ошибки случаются (`fetch failed` у отдельных сайтов), поэтому упавшую ссылку я сначала перепроверяю повторным прогоном, а не сразу удаляю.
- **RU и EN согласованы.** У каждого текста есть обе версии, а термины глоссария в разметке `[[id|текст]]` в русском и английском тексте должны совпадать.
- **Баланс сложности.** В каждой теме не меньше 15% вопросов уровня senior — иначе тема превращается в «вопросы для джуна».
- **Контраст.** Цвета акцентов тем проверяются на контраст WCAG ≥ 4.5 к фону в светлой и тёмной теме.
- **Заметки о версии.** Версия в `package.json` должна совпадать с первой записью «Что нового», а в `CHANGELOG.md` — быть секцией.

## CI и доставка

Всё это запускается одной командой `npm run verify:content` — сначала type-check, потом проверка банка. В GitHub Actions она идёт на каждый пуш: Node той же версии, что локально, и системный Chrome раннера. Без Chrome проверка в CI падает, а не пропускает вопросы — иначе можно незаметно перестать проверять CSS.

Тот же прогон стоит перед публикацией контента. Вопросы доставляются в приложение паками через GitHub Pages: приложение раз в 12 часов скачивает новый пак и применяет его при следующем запуске, без релиза в стор. Workflow публикации сначала выполняет `verify:content` и только потом собирает пак, так что непроверенный вопрос до пользователя не доходит.

Одна история про собственный CI. Проверка иногда падала с пустой ошибкой «код упал:» — на одном случайном вопросе, при повторе всё зелёное. Причина оказалась банальной: на запуск фрагмента кода давалось 5 секунд, а когда параллельно шла сборка Android-приложения и работал эмулятор, процесс `node` не успевал даже стартовать и убивался по таймауту. Таймаут поднял до 20 секунд, а сообщение теперь честно говорит «не уложился в 20 с». Нестабильная проверка опаснее отсутствия проверки: к красному прогону, который «иногда бывает», быстро привыкаешь.

## Итого

- 334 вопроса из 808 проверяются машиной: Node.js, компилятор TypeScript, headless Chrome и git.
- Каждый вид проверки — несколько десятков строк поверх стандартных инструментов, без тестовых фреймворков: `child_process`, TypeScript Compiler API, `chrome --dump-dom`, bash.
- Проверять нужно не только правильный ответ, но и то, что неправильные варианты действительно неправильны.
- Самые ценные находки — там, где реальность расходится с ожиданием: браузер со спецификацией, git с прошлой версией, Node с документацией.
